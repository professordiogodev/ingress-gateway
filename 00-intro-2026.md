## What is a Controller?

Before anything else, you need to understand the pattern that everything in Kubernetes is built on: the **reconciliation loop**.

A **controller** is a program that:
1. Watches the Kubernetes API for objects it cares about
2. Compares the current state of the world to the desired state those objects describe
3. Takes action to close the gap
4. Repeats forever

```
┌─────────────────────────────────────────────────────────────┐
│                      Controller loop                        │
│                                                             │
│  Watch API ──▶ Compare desired vs actual ──▶ Take action   │
│      ▲                                            │         │
│      └──────────────── repeat ────────────────────┘         │
└─────────────────────────────────────────────────────────────┘
```

**Example:** The Deployment controller watches `Deployment` objects. When you set `replicas: 3` and 0 pods exist, it creates 3. When a pod dies, it creates a replacement. It never stops. This is called **level-triggered reconciliation** — it doesn't react to events, it just constantly asks "is the world what it should be?"

Every component in these labs is a controller:

| Controller | What it watches | What it does |
|-----------|----------------|--------------|
| **NGINX Ingress Controller** | `Ingress` resources | Rewrites `nginx.conf`, reloads NGINX |
| **NGINX Gateway Fabric** | `Gateway` + `HTTPRoute` resources | Configures NGINX proxy rules |
| **cert-manager** | `Certificate` + `Ingress` resources | Calls Let's Encrypt API, creates/renews Secrets |
| **external-dns** | `Ingress` + `HTTPRoute` resources | Calls Route53 API to upsert DNS records |

You never script "create DNS record, then create cert, then configure load balancer." You apply YAML describing what you want, and controllers race to make it real.

## The Rise and Fall of Ingress NGINX

### How it started (2016)

In the early days of Kubernetes, exposing an application meant a **Service of type `LoadBalancer`** — one cloud load balancer per app. At even moderate scale, this became expensive and unmanageable. The community needed a smarter routing layer.

**Ingress** was added in Kubernetes 1.2 (2016) as the answer: declare HTTP routing rules in YAML, let a controller implement them. The **Ingress NGINX controller** (from the Kubernetes community project, not to be confused with F5/NGINX Inc's separate controller) became the dominant implementation almost immediately. It was flexible, well-documented, cloud-agnostic, and free.

For nearly a decade it ran everywhere — from homelabs to production clusters at Airbnb, Pinterest, and GitHub. It powered **billions of requests** worldwide. On many hosted Kubernetes platforms (GKE, EKS, AKS offerings), it was the default.

### How it ended (2025–2026)

**November 2025:** The Kubernetes Security Response Committee and SIG Network published an official announcement: Ingress NGINX would be retired. Best-effort maintenance until March 2026. After that: no releases, no bugfixes, no security patches. Repositories made read-only.

**March 2026:** Ingress NGINX is officially retired. It's dead.

The reasons, as stated in the official announcement:

**1. Technical debt became a security liability**  
The features that made Ingress NGINX great — particularly the ability to inject arbitrary NGINX configuration via "snippets" annotations — became impossible to secure. CVE-2025-1974 was a critical remote code execution vulnerability that exploited the snippets feature. The fix required removing flexibility that many users depended on. What was once "powerful customization" had become "unapologetic attack surface."

**2. Two people were maintaining infrastructure running on millions of clusters**  
For years, Ingress NGINX was maintained by one or two people, on their own time, after work hours and on weekends. The project's enormous popularity never translated into proportional contributor interest. When the maintainers announced they were winding down, nobody stepped up to replace them.

**3. The planned replacement (InGate) never shipped**  
The maintainers had announced a successor project called InGate, built on Gateway API from the ground up. It never reached maturity. InGate is also retired.

**4. Gateway API made Ingress obsolete**  
Gateway API (stable since Kubernetes 1.28, October 2023) solved every architectural problem Ingress had. Once it was stable, there was no technical argument for investing more engineering in Ingress.

> **The official SIG Network recommendation (as of March 2026):** *"All Ingress NGINX users should migrate to Gateway API or another Ingress controller immediately."*

## Why Labs 1 and 2 Still Teach Ingress

You might wonder: if Ingress NGINX is retired, why are Labs 1 and 2 using it?

Three reasons:

**1. The cluster still runs it, and it still works**  
Retired doesn't mean broken. The images exist, the Helm chart works, and it will continue routing traffic correctly — it just won't receive security updates. In a teaching environment with no sensitive data, this is fine.

**2. The industry is swimming in Ingress resources right now**  
Every company that has run Kubernetes for more than two years has Ingress YAML everywhere. When you join a team in 2026, you will encounter Ingress resources. Understanding them is not optional.

**3. Understanding what you're migrating from makes the migration make sense**  
You can't appreciate Gateway API's design until you've felt the pain of NGINX annotations. Labs 1 and 2 give you that context. Labs 3 and 4 are where the punchline lands.

**Note:** If you need a production-grade ingress controller that's still maintained, the **F5/NGINX Inc** controller (`nginxinc/kubernetes-ingress`) is a separate project from the retired community controller. AWS ALB Ingress Controller is also actively maintained. But the community consensus is: go to Gateway API.

## Gateway API: The Actual Future

**Gateway API** is the Kubernetes-standardized replacement for Ingress. It's been stable (v1) since Kubernetes 1.28 (October 2023) and is now implemented by every major networking vendor.

### What Ingress gets wrong

```yaml
# Lab 1: rewrite a path in NGINX Ingress
nginx.ingress.kubernetes.io/rewrite-target: /

# Same thing in AWS ALB controller
# (not supported — use different annotation)

# Same thing in Traefik
# traefik.ingress.kubernetes.io/router.middlewares: default-stripprefix@kubernetescrd
```

These annotations are not portable. Switching controllers means rewriting YAML. Your routing rules are locked to your implementation.

```yaml
# Lab 3: rewrite a path in Gateway API
filters:
  - type: URLRewrite
    urlRewrite:
      path:
        type: ReplaceFullPath
        replaceFullPath: /
```

This is the same regardless of whether the controller is NGINX, Envoy, Cilium, or anything else. **One API, every implementation.**

### The role-oriented model

```
GatewayClass  → Platform/Infra team   "which controller to use"
  Gateway     → Cluster Admin          "which ports and hosts to expose"
    HTTPRoute → Developer              "which paths go to which services"
```

Developers can manage their own routing rules without access to cluster-level resources. Platform teams can enforce policies at the Gateway level. This is how large organizations actually want to operate.

### What Gateway API supports that Ingress never could

- **gRPC routing** (`GRPCRoute`) — native
- **TCP/UDP routing** (`TCPRoute`, `UDPRoute`) — native
- **Traffic splitting** — 80% to v1, 20% to v2, built in
- **Header-based routing** — match on any request header
- **Request/response transformation** — add/remove/rewrite headers
- **Retry budgets** — standardized retry policies (added in v1.3, 2025)
- **CORS** — standardized CORS configuration (added in v1.3)

## The 2026 Controller Landscape: What Actually Gets Used

### Tier 1: Pure routing (no mesh)

**NGINX Gateway Fabric** (F5/NGINX Inc)  
Gateway API implementation backed by NGINX. This is what Labs 3 and 4 use. Actively maintained, good docs, familiar if you know NGINX. Popular with teams migrating off ingress-nginx who want continuity.

**Envoy Gateway** (CNCF)  
The CNCF's own Gateway API implementation backed by Envoy. Strong enterprise adoption. Backed by Tetrate, Solo.io, and cloud providers. The "politically neutral" choice if you don't want to depend on a single vendor.

**AWS Load Balancer Controller**  
Creates real ALBs or NLBs directly. Deep AWS integration: WAF, Cognito, ACM. Moving toward Gateway API. Preferred by teams that want TLS fully managed by AWS and don't want to run cert-manager.

**Cilium Gateway API**  
If you're already running Cilium as your CNI (increasingly the default on GKE, EKS, AKS), its Gateway API implementation is free and eBPF-based. No additional controller to manage.

### Tier 2: Service Mesh (adds mTLS, observability, advanced traffic policies)

A **service mesh** adds a network layer between your pods that provides:
- **Mutual TLS (mTLS)** — every connection between services is encrypted and authenticated, without any code changes
- **Automatic observability** — metrics, traces, and logs for all traffic, without instrumenting your code
- **Traffic policies** — retries, timeouts, circuit breaking, canary deployments

**Istio** — The dominant enterprise service mesh. Used at Google, Airbnb, Lyft, eBay. Graduated from CNCF in 2023. Implements Gateway API natively (so your HTTPRoutes work with Istio's gateway, not just NGINX).

The historical knock on Istio: the **sidecar model** injects an Envoy proxy into every pod. This adds ~50–100ms of latency per hop and significant memory overhead. Istio's answer: **Ambient Mode** (stable in Istio 1.22, 2024). No sidecars. A per-node `ztunnel` handles L4 mTLS, and optional `waypoint` proxies handle L7 policies. New Istio deployments in 2026 start with Ambient Mode.

**Linkerd** — Lightweight Rust-based mesh. Smaller feature set than Istio, simpler to operate. Popular with teams that need mTLS and basic observability but don't want Istio's complexity. Uses a Rust data plane for lower overhead than Envoy.

**Cilium** — The most disruptive option. Started as a CNI (the low-level network plugin), added service mesh capabilities using **eBPF** instead of sidecars or proxies. eBPF runs in the Linux kernel, so Cilium can observe and control network traffic without any user-space proxy overhead. In 2025–2026, Cilium is the **default CNI on GKE, EKS, and AKS**. Teams that run Cilium for their CNI often also enable Cilium's service mesh features, eliminating the need for a separate mesh installation.

## How Companies Are Actually Adapting Right Now (May 2026)

The March 2026 Ingress NGINX retirement sent a shockwave through the industry. Here's what different types of companies are doing:

### Large enterprises (thousands of services, multiple clusters)

These companies have the most Ingress YAML and the most to lose. Most of them already knew this was coming — the November 2025 announcement confirmed it — and have been running migration projects since early 2026.

**What they're doing:**
- Auditing how many clusters still run ingress-nginx (`kubectl get pods --all-namespaces --selector app.kubernetes.io/name=ingress-nginx`)
- Converting Ingress resources to HTTPRoutes namespace by namespace, using migration tooling (the Gateway API project published an `ingress2gateway` CLI tool)
- Running Ingress and Gateway API in parallel during the transition — both live in the cluster, routes gradually move over
- Deploying **Istio Ambient Mode** for the mTLS and observability story
- Hiring engineers with Gateway API experience (this is in job descriptions now)

**Timeline:** Most large enterprises target Q3 2026 completion for the ingress-nginx removal. Some are still on Q4. A few are in denial.

### Cloud-native startups (born post-2023)

These companies never ran ingress-nginx. They started with Gateway API from day one, often with Cilium as the CNI (because that's what GKE and EKS ship with now) and Cilium's Gateway API implementation for routing.

**What they're doing:** Nothing — they're already there. Their only networking exposure to Ingress is when an engineer looks at old blog posts.

### Mid-size companies migrating from ingress-nginx

This is the most common situation. A company with 5–50 engineers, running Kubernetes for 2–4 years, with ingress-nginx as the default they never questioned.

**What they're doing:**
- Option A: Migrate to **Envoy Gateway** or **NGINX Gateway Fabric** — lowest friction because the concepts are similar, the annotations become HTTPRoute rules, and they get Gateway API benefits going forward
- Option B: On AWS, migrate to **AWS Load Balancer Controller** with Gateway API — offload TLS to ACM, reduce operational burden
- Option C: **Cilium** all-in — if they're already thinking about replacing their CNI, Cilium handles routing, network policy, and optional mesh in one install

**The ingress2gateway tool** (from the Kubernetes Gateway API project) automates much of the mechanical conversion. It reads existing Ingress resources and outputs equivalent HTTPRoute + Gateway YAML. Manual review is still required for annotation-heavy configs.

### Companies that ignored the warning (there are many)

Some teams saw the November 2025 announcement, acknowledged it, and didn't act. As of May 2026:
- Their ingress-nginx is frozen at whatever version they were running in March 2026
- They're accumulating unpatched CVEs
- Their compliance team is starting to ask questions
- Their platform engineers are quietly looking for new jobs

This is not hypothetical. Every major retirement announcement has this cohort. The difference now is that **there is no security patch coming**. Ever. The urgency is real.

## What Hiring Managers Are Looking For in 2026

Kubernetes networking job descriptions in 2026 look very different from 2023. Here's what appears:

**Things that used to be required, now becoming irrelevant:**
- "Experience with NGINX Ingress Controller"
- "Writing ingress annotations"
- "Debugging nginx.conf issues"

**Things that are now required:**
- "Gateway API (GatewayClass, Gateway, HTTPRoute)" — appears in most platform engineer JDs
- "Cilium or Istio" — one of these; which one depends on the company's stack
- "cert-manager for TLS lifecycle" — nearly universal
- "eBPF fundamentals" — appearing at mid/senior level
- "Ingress to Gateway API migration experience" — explicitly called out in many 2026 postings

**The migration project itself is a resume item.** If you led or contributed to a company's Ingress → Gateway API migration, that's concrete experience that every hiring manager in 2026 recognizes as valuable. The timing means that senior engineers who did this migration in early 2026 have a meaningful advantage.
